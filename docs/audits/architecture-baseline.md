## Benchmark methodology

Use the current fixture preparation and five task classes: a small bug, a simple feature, a medium refactor, a multi-module change, and a change with protected verification inputs. Freeze the task text, acceptance cases, initial commit, dependency lock, backend and host settings. Run native execution, the baseline plugin revision, and the refactored revision on separate fixtures. Rotate their order across repeated trials. Keep the model choice or model selection policy explicit for each arm.

Run the same independent evaluator against the resulting snapshots. Record pass or fail, exit codes, changes to protected inputs, time to verified completion, attempts, interventions, and regressions. Record input, cached input, output, and timing for routing, implementation, verification, retries, and supporting calls. Retain time and usage for failed or interrupted trials and label environmental stops. Keep subscription windows and list-price estimates separate from provider billing. Use `UNKNOWN` when a provider omits a count. Fix the pricing date and model IDs before comparing estimates.

Report success rates and total usage, spend, and elapsed time per verified task, with the number of trials and dispersion. No native-versus-baseline-versus-refactor trial was run for this audit. The available evidence cannot establish whether the routing overhead pays off.

An independent evidence pipeline would duplicate attempt, resume, and history state before Claude can supply equivalent host evidence. Narrow CI credentials without adding paid or model-dependent checks.

## Proposed task contract

Use one versioned envelope for both adapters. The host assigns `id`, `repository`, `cwd`, and `status`. The caller supplies `task`, an optional `allowedPaths` list, and `acceptance`. Trusted settings supply `protectedPaths`, named `checks`, and `limits` for attempts and time. Host policy assigns `risk` and `profile`. A finished attempt adds `evidenceRefs`. Keep repository context out of the envelope.

Reject unknown versions, invalid types, empty task text, absolute or escaping scope paths, and invalid limits before execution. Canonicalize the repository and working directory at the host boundary. Accept older inputs through the current path. Require explicit authorized scope before moving a legacy caller into a new execution profile. Resolve named checks in trusted settings. Never execute a command supplied by a model as part of the contract.

| Proposed profile | Policy decision | Completion evidence |
| --- | --- | --- |
| `DIRECT` | Low risk with known scope, reversible changes, and no sensitive operation. Use the current agent under its existing host permissions. | Applicable lightweight checks, with omissions recorded. |
| `MANAGED` | Moderate risk. Use one native agent and explicit acceptance criteria. | Runner-observed required checks. Independent review when the checks leave acceptance unanswered. |
| `ISOLATED` | High risk, uncertain boundary, or significant external impact. Require an isolated workspace and a verified host sandbox. Request human approval where the operation requires it. | Required local checks, independent CI, and the approval record where applicable. |

Risk considers data loss, credentials, deployment impact, rollback, and verification confidence separately from scope size. The contract expresses policy. The native runner or a hardened container must enforce access, and delivery must compare the candidate against the authorized scope. Unavailable required isolation blocks the requested profile. These profiles are a design proposal. The existing `DIRECT` result still refers to the legacy context-based flow.
