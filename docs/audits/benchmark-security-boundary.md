# Benchmark security boundary

November 19, 2026. This report covers the trusted-controller boundary for the Execution v2 benchmark on WSL2. It keeps only what is still open. Every required Codex security condition passed offline through the real `codex exec` tool path using the versioned wrapper `tests/e2e/bench-boundary.mjs` (`BOUNDARY_VERSION = 1`) and `tests/e2e/codex-exec-canary.mjs`. Claude stays **BLOCKED**, and no pilot slot has run (0/8 pilot, 0/102 formal).

## Open items

| Area | Still open | Evidence |
| --- | --- | --- |
| Codex sign-in and live canary | Both Linux controller clients are signed out (`codex login status` prints `Not logged in`, `claude auth status` reports `loggedIn: false`, each exits `1`). Only the user can sign in. Use a dedicated benchmark account in a separate WSL terminal with the controller block in [benchmark-environment.md](../benchmarks/benchmark-environment.md#sign-in-interactively-from-the-controller), then run `codex login status` in the same environment. Before the first pilot slot, repeat `codex-exec-canary.mjs` once against the real provider with fake canaries to confirm the signed-in configuration resolves to the same profile. | `tests/e2e/codex-pilot.mjs` (the driver exists and waits for this) |
| Operation denial | Host integrity passes, but outside writes, `mkdir` and `unlink` still succeed in a private layer that is discarded afterwards. This applies to the strict verifier sandbox, `codex sandbox` under the wrapper, and Claude Bash under managed settings. A test that expects an outside write to fail can behave differently from the host. | `node tests/e2e/codex-sandbox-smoke.mjs` still exits `1` with `write: ALLOWED`. `tests/e2e/host-integrity-smoke.mjs` covers host integrity. |
| Codex tools outside the wrapper | The legacy `--sandbox read-only` and `workspace-write` modes let tool commands read files outside the workspace, including `$CODEX_HOME/auth.json`. Only the wrapper's managed profile removes this, so it holds for benchmark trials and nowhere else. | `scripts/codex-exec.mjs` passes `--sandbox <mode>` unchanged |
| Codex sub-agents | `codex exec` rejected `spawn_agent` with `agent thread limit reached`, with or without the wrapper. The path is unreachable with the runners' default configuration, but it was not proven confined. | `tests/e2e/codex-exec-canary.mjs` |
| Claude legacy Workflow | The legacy Workflow in an interactive host session has not been exercised. The v2 `--tools` list does not offer it. | `tests/e2e/claude-tool-canary.mjs` |
| Claude hooks | Command hooks run unsandboxed in the controller by design. No hook was exercised. The legacy plugin's hooks are trusted controller code, and `allowManagedHooksOnly` would remove them from the legacy arm. | `hooks/hooks.json` |
| Claude v2 worker edits | Worktree writes were denied in both canary runs. The v2 Claude worker needs fixture-specific `Edit` allow rules, and their interaction with the managed settings is **UNVERIFIED**. | `scripts/claude-exec.mjs` (`--tools`, `--permission-prompts none`) |
| Claude logs and live run | Claude logs were not scanned for credentials, and no live run has happened. Authenticate Claude with file-based logins only. Never use `ANTHROPIC_API_KEY` without the `sandbox.credentials.envVars` deny rule, because Claude Bash can otherwise read it. | `tests/e2e/bench-boundary.mjs` (`claudeManagedSettings`) |
| Claude file tools | Read, Edit, Write, WebFetch, hooks and local MCP servers sit outside Claude's Bash sandbox and are checked only by permission rules. Official documentation does not say whether Workflow agents are covered. [Sandboxing](https://code.claude.com/docs/en/sandboxing) | Offline canary: the Agent sub-agent received the same denials |
